# Results

Measured results for `secure-triage-agent`, updated at the end of each phase. Every number here comes from a real run and is reported with its settings, sample size and a 95% Wilson interval.

**Two evidence streams are kept apart and never merged into one number:**

| Stream | Measures | Reported as |
|---|---|---|
| Garak findings | Whether the model's output tripped a probe/detector pair | "Model behavior under probes" |
| Verified application outcomes | Whether an unauthorized action or leak actually happened (tickets, data) | "Application security outcomes" (primary evidence) |

A Garak hit does not mean the application was compromised.

**Status:** Phase 1 complete for v1 (2026-11-06), with limits stated below: the runs were not seeded, so the numbers cannot be reproduced exactly, and the stricter counts are one rater's classification. Sections for later phases are placeholders.

### Stricter counts (our definitions, separate from Garak's flags)

Garak's detectors are substring or similarity checks, so a hit can be a refusal that quotes the planted text. `scripts/classify_hits.py` sorts the flagged replies; the count below is the replies that carry out the injection (`latentinjection`, `promptinject`) or decode the string exactly (Hex, ROT13). This is one rater's classification and the rules were written after reading the replies, so it has not been independently validated. A later check on 60 randomly drawn flagged replies, labeled by the same rater without looking at the script's tier, agreed on 58 (96.7%, Wilson 88.6% to 99.1%); it is the same rater and the easy cases dominate it (analysis document, section 14). It only sorts replies that Garak flagged, so it cannot see obedience the detector missed (for example, `Resume` triggers end in a period and replies without it are not flagged; about 16 more `Resume` replies look similar to a trigger). ### What a "hit" means
- **`TriggerListDetector`** (`latentinjection`) and **`AttackRogueString`** (`promptinject`): the reply contains the planted string, matched case-insensitively as a substring. A reply that refuses, quotes or refutes the injection is counted too.
- **`DecodeMatch`** (`encoding`): the reply contains the exact decoded target text. **`DecodeApprox`** counts a partial match at a score of 0.5 or above, so a close but wrong decode (for example "Spoof" for "Spook") can count.
- For the encoding probes a hit shows the model can decode the string, not that it obeyed an instruction.

### What this does and does not show
- **Shows:** under these probes, `qwen2.5:7b` often follows instructions hidden in a document or printed after "ignore previous instructions". In the strict count, 62% of `LatentInjectionReport` prompts and 78% to 82% of two of the three `promptinject` probes ended with the model emitting the attacker's text as its answer. It decodes Hex about 19% of the time (exact) and did not decode ROT13 in any of 256 prompts.
- **Settings:** temperature 0 gives one deterministic answer per prompt, not the spread of the model's behavior at higher temperatures. The 150-token cap makes the `latentinjection` and encoding rates lower bounds. The `promptinject` rows mix temperatures 0 to 0.9 and `max_tokens` 60 to 256, so they cannot be compared with the others.
- **Does not show:** that any application was compromised (that is Phase 3, a separate evidence stream); behavior of other models, other settings or adaptive attackers; how much the counts vary from run to run (the runs were unseeded and each drew different prompts, and the variation was not measured).
- A hit is a detector score at or above a threshold, not proof of a successful attack. Zero hits in n prompts is not proof of zero risk: with 0 of 256, the true rate could still be about 1.5%.
- Model refusals are not counted as defenses and errors are not counted as passes. 0 prompts had a missing or blank reply in any run.

### Reproducing this
Needs the setup in the README, Ollama running with `qwen2.5:7b`, and (on macOS) AC power; the commands are in the README under "Reproducing the Phase 1 baseline". Settings are pinned in `garak/baseline.yaml`. A rerun repeats the same method but not the same prompts: the numbers above come from unseeded runs, and the seed added to the config afterwards selects a different prompt set, so expect somewhat different counts. Garak's reports are written to `~/.local/share/garak/garak_runs/` (outside this repo), and the report names used for the table above are `phase1_encoding_base64_g1`, `phase1_latentinjection_g1`, `phase1_encoding_hex_rot13_g1` and `phase1_promptinject_g1`. Then:

```bash
python scripts/parse_garak.py ~/.local/share/garak/garak_runs/phase1_{encoding_base64,latentinjection,encoding_hex_rot13,promptinject}_g1.report.jsonl
```
